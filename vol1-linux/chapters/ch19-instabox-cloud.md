# 第 1 章 搭建实验环境：InstaBox 云电脑

> 第 0 章我们说清楚了"去哪、为什么"。从这一章开始动手：先在云端开一台属于你自己的 Linux 机器。全书所有命令都在这台机器上验证，所以本章的任务只有一个字——把环境搭好。搭好之后，你随时可以在任何一台电脑上（公司的、寝室的、机房的）敲三下行命令就回到你的服务器，作业写没写完，只取决于你敲没敲。

> **本章目标**
> - 能在 InstaBox 上完成注册、安装命令行工具（CLI）、登录，并创建出自己的云电脑 `book`。
> - 能用五条验货命令（nproc、free -h、df -h /data、docker info、uname -a）逐条读出这台机器的配置与真实身份，并说清免费档的每一项配额。
> - 能熟练使用暂停/恢复/快照三板斧管理实验环境，并说清 30 分钟自动暂停、10 分钟 exec、10 MiB 传输等六条限制的应对办法。

## 1.1 为什么用云电脑，而不是本地虚拟机

过去的教程会让你在电脑上装 VirtualBox、VMware，下一个几个 GB 的镜像，再一步步点鼠标。可以，但没必要。这本书选择云电脑，理由有四条，每一条都踩在初学者的真实痛点上：

**第一，零配置。** 不用下载镜像、不用划磁盘、不用调网络适配器。你在浏览器里点几下、命令行里敲一条 `create`，一台装好的 Debian 13 就归你了。初学者最大的敌人从来不是"命令难"，而是卡在环境上三天，热情先没了。

**第二，不占本机资源。** 虚拟机吃的是你这台电脑的内存和磁盘——你本来可能就只有 8 GB 内存，再开一台虚拟机，两边都卡。云电脑跑在云端，你的笔记本只负责显示一个终端，风扇都不带动一下的。

**第三，坏了就重建。** 这是最该建立的心态，业内叫"宠物 vs 牲畜"（Pets vs Cattle）：把服务器当宠物，每台都取名字、悉心照料、舍不得重装；把服务器当牲畜，按需取用、坏了就换、批量管理。SRE 的全部高级能力——自动化、不变的基础设施、无人值守发布——底子都是这个思维。云电脑是练习这种思维的完美场所：你把系统搞崩了，删了重建一台只要几分钟，而在虚拟机上你还要先学会怎么修好它才能继续往下学。

**第四，与生产环境同构。** 你以后上班要伺候的服务器，八成是"云端的一台 Linux，用 SSH 连上去操作"。本书的实验方式——创建机器、SSH 登录、命令行操作、暂停计费——和你在云厂商那里租一台 VPS（Virtual Private Server，虚拟专用服务器）的流程几乎一样。第 12 章《网络配置与远程管理》我们真的会租一台 VPS 做对照，你会发现连提示符都长得一样。

> **SRE 贴士**："随手创建、随手销毁"是现代基础设施的基本操作单元。你以后会频繁创建机器（开发环境、测试环境、压测环境），也会频繁销毁它们。本书从第一章就让你把这个动作的成本降到"一条命令"，就是为了让你尽早习惯"资源是流水，不是家具"。

> **生产 vs 实验室**：实验室里删机器重建是政治正确；生产上"删了重建"之前，你要确认数据有没有备份、流量有没有切走、域名解析有没有改。这就是为什么本书到第 16 章《防火墙与数据备份》才正式讲备份与 3-2-1 原则——本章请先尽情享受"随便造"的自由，但请记住：**自由的边界是你有备份可退。**

## 1.2 注册与登录

打开官网 `instabox.sh`（InstaBox 是一家 YC（Y Combinator，美国知名创业孵化器）孵化的公司做的"AI Agent 用的云电脑"，我们把它当普通 Linux 服务器用）。首页用 **Google 账号或 GitHub 账号登录**（走 OAuth（开放授权协议，Open Authorization）第三方登录，不用在平台单独设密码）。

可能遇到的情况是**排队**：如果平台在控制放号，新用户会进入等待名单（waitlist），按批次开放。遇到等待名单时有三件事可做：一是按页面提示留下邮箱，轮到你会有通知；二是隔几天用同一个账号再登一次看看；三是别干等——等待期间你可以先把 1.3 节的命令行工具装好，并读完第 3 章《首次登录：SSH、终端与第一组命令》，等机器到手直接上手。

登录成功后，你会看到一个网页控制台（Web Console），核心是一个"Computer"页面，列出你名下的机器。现在我们把这个页面放一放，改用更适合初学者的方式——命令行工具（CLI，Command-Line Interface，命令行界面）来操作，因为它和书里的命令一一对应，也方便你以后写脚本。

## 1.3 安装命令行工具 CLI

命令行工具有两种装法，按你的电脑情况二选一。

**装法一：curl 一把梭（macOS / Linux / Windows 的 Git Bash）**

```bash
curl -fsSL https://api.instabox.sh/install.sh | sh
```

先把这行命令拆开看懂，不许稀里糊涂地回车——这是本书的第一条命令，也顺便把 `curl` 认识了：

| 片段 | 含义 |
| --- | --- |
| `curl` | 命令行里的"下载器"，把网址的内容拉下来 |
| `-f` | fail：HTTP 出错时直接失败，不把错误页面当正常内容 |
| `-s` | silent：不显示下载进度条 |
| `-S` | show-error：配合 `-s`，真出错时把错误原因显示出来（否则哑巴失败） |
| `-L` | location：对方返回跳转时，自动跟到新地址 |
| `https://api.instabox.sh/install.sh` | 安装脚本的网址 |
| `\| sh` | 把下载到的内容直接交给 `sh` 执行 |

执行完，CLI 就被装到系统里（一般在 `/usr/local/bin/instabox`），是个单文件程序。输出是示意，大意如下：

```text
installing instabox cli /usr/local/bin/instabox ... done
installed. next: run 'instabox login'
```

（实际文案以安装脚本为准，看到类似 "installed" 的收尾就是成功了。）

> **警告**：`curl 网址 | sh` 这种"下载完直接执行"的写法，是供应链攻击最经典的入口——哪天这个域名、这个脚本被人动了手脚，你的机器就交出去了。**第一次装任何工具，请先把脚本拉下来看一遍再跑**：`curl -fsSL https://api.instabox.sh/install.sh -o /tmp/ib-install.sh`，然后 `less /tmp/ib-install.sh` 通读一遍，确认里面没有可疑操作（比如偷偷读你的 `~/.ssh`、往 bashrc 里塞东西），再 `sh /tmp/ib-install.sh`。多花三分钟，养成这个习惯，是 SRE 的基本素养——生产上这条纪律叫"不部署无法审计的代码"。

**装法二：npx（本机有 Node.js 时，Windows 上最省事）**

```bash
npx instabox@latest sh
```

`npx` 是 Node.js 自带的"临时运行 npm 包"的工具：第一次运行它会提示要不要下载 `instabox` 这个包（回车确认即可），之后每次运行都自动保持最新版（`@latest`）。它的好处是**不经安装、不留垃圾、天然跨平台**，所以在 Windows 上最省事——PowerShell 里直接能跑，不必纠结有没有 `sh`、`/usr/local/bin` 这些 Linux 概念。

如果你的电脑没有 Node.js：去 nodejs.org 下载 LTS（长期支持版）安装包，一路下一步即可（版本号以官网当前 LTS 为准，别装最新 Current 版，企业工具链求稳）。

**macOS / Linux 用户**也可以凑热闹用装法二，但装法一更干净。两条路任选其一，别重复装两遍，用哪个顺手用哪个。

装完先自检，确认它真的在：

```bash
instabox --version    # 出版本号就是装好了
instabox --help       # 列出所有子命令，以后忘了语法就回来查它
```

```text
instabox version 1.x.x        ← 版本号以你的机器为准
Usage: instabox <command> [options]

  create       Create a new machine
  ssh          SSH into a machine
  ...
```

> **SRE 贴士**：`命令 --help` 是初学者的救命稻草，也是老手的习惯。本书讲的是"现在这个版本的用法"，而 CLI 迭代快，拿不准某个参数时，`instabox create --help` 永远比搜索引擎里的过期博客可靠。**把 "--help 先看一遍" 变成肌肉记忆，你能挡掉一半"参数写错"的报错。**

## 1.4 登录授权：设备码流程

第一次用 CLI 前要先登录，把我们刚注册的账号授权给这台终端：

```bash
instabox login
```

它走的是设备码（device code）流程——命令行里不方便输密码，所以它的姿态是：命令行负责"喊话"，浏览器负责"登录"。执行后你会看到类似这样的输出（示意，网址与设备码以你的实际输出为准）：

```text
To sign in, open this page in any browser (phone is fine):

    https://instabox.sh/auth/device   ← 以实际输出为准

Then enter this code:

    QW3R-T5YU                        ← 以实际输出为准

Waiting for authorization... authorized! You are signed in as your-email@example.com.
```

三个要点：一，**任何设备上的浏览器都行**——手机扫码/输入设备码尤其方便；二，设备码通常有效期很短，看到了就立刻输，别放着；三，看到 `authorized` 或类似字样就是成功，之后在**同一台电脑上**再用 CLI 就不用重复登录了。换电脑、换终端，重新 `instabox login` 一次即可。

登录状态可以用 `instabox whoami` 之类的自检命令确认（具体子命令名以 `instabox --help` 为准）。

## 1.5 创建你的第一台云电脑

全书统一把机器命名为 `book`，所有命令里出现的 `book` 都是它。创建只需一行：

```bash
instabox create --name book
```

| 片段 | 含义 |
| --- | --- |
| `instabox` | CLI 本体 |
| `create` | 子命令：创建一台新机器 |
| `--name book` | 给这台机器起名，`--name` 的值自己定，本书固定用 `book` |

输出是示意，大意如下（字段以平台实际输出为准）：

```text
Creating machine 'book' (template: agent-browser, default)...
  vcpu: 4 / memory: 8 GiB / disk: 20 GiB persistent
Machine 'book' created and starting... status: running
Try:  instabox ssh book
```

看到 `running` 或类似状态，机器就是你的了。之后本书的所有命令，默认都是在这台 `book` 上执行。

**关于模板（Template）**：模板 = 开机自带软件集的"系统镜像"。默认模板 `agent-browser`（等同于 `universal` 档）已经预装了我们卷 1 到卷 4 几乎全部要用的东西：Docker、Node.js 22、Python + uv、Go、Rust、C 工具链，外加桌面环境和 Chromium 浏览器。够用，非常好用。

但有一个免费档的限制必须现在就知道：**免费档不能指定模板。** 加 `--template universal` 这样的参数会被平台拒绝，报 `403 template_not_allowed`（详见 1.9 节的坑一）。唯一沾"指定模板"边的场景是从快照开机——因为快照里已经固化了环境本身（详见 1.8 节）。

## 1.6 验货：五条命令读出这台机器的底细

机器到手，第一件事不是急着敲命令玩，而是**验货**——确认平台给的配置和承诺一致。这也是云上排障的第一课：**不要盲信任何"应该有"，先验证。** 依次执行下面五条命令，我们逐条解读。

### 1.6.1 nproc：有几个核

```bash
nproc
```

```text
4
```

`nproc`（number of processors）报告当前进程可见的 CPU 处理单元数量。输出 `4`，和免费档"4 vCPU"对上了。注意"vCPU"是超线程/共享形态的逻辑核，和物理核不是一回事，但对我们的练习来说没有区别。这一条顺带建立了你的第一个肌肉记忆：**报告数字的机器语言，常常就是一个词加一个回车。**

### 1.6.2 free -h：内存有多少，谁在占

```bash
free -h
```

```text
               total        used        free      shared  buff/cache   available
Mem:           7.6Gi       1.1Gi       4.9Gi        12Mi       1.8Gi       6.4Gi
Swap:              0B          0B          0B
```

一行一行念：

| 列 | 含义 | 初学常见误读 |
| --- | --- | --- |
| `total` | 物理内存总量，约 7.6 GiB | 不是说好 8 GiB 吗？被固件、内核预留了一部分，**7.x GiB 完全正常**，不是平台少给了 |
| `used` | 已用内存，含各类程序 | 高不一定危险，Linux 的设计是"内存闲着才是浪费" |
| `free` | 完全没被碰过的内存 | 这一列小不代表不够用 |
| `shared` | 多进程共享的内存（如 tmpfs），通常很小 | — |
| `buff/cache` | 磁盘缓存，提速用的 | **它不是"被占走了"，是随时可以还回来的** |
| `available` | 新程序实际还能用到多少 | **判断内存够不够，只看这一列** |

两个参数：`-h` 表示 human-readable（人类可读，GiB/MiB 而不是一串字节数），默认单位是 KiB。最后一行 `Swap` 全 0：这台机器没有配 swap（交换分区，内存不够时拿磁盘顶），符合云电脑的常见配置，第 11 章《磁盘与存储管理》我们会讨论它。

新手经典误判：看到 total 是 7.6GiB 就去工单"我买的 8G 怎么少了 400M"——省下这个功夫，那是内核和固件的预留，全世界所有 Linux 都这样。

### 1.6.3 df -h /data：持久盘到位了吗

```bash
df -h /data
```

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/vdb         20G   28K   20G   1% /data
```

`df`（disk free）报告文件系统的磁盘用量；`-h` 同上，人类可读；后面跟 `/data` 表示"只报告 /data 所在的那个文件系统"，不加参数会把 `/`、`/boot`、`/etc` 等十几个文件系统全列出来，刷屏且找不到重点。

从右往左读：`Mounted on` 是挂载点 `/data`，说明这个文件系统挂在 `/data` 上；`Size` 20G，和"20 GiB 持久盘"对上了；`Used` 才 28K，一台全新的干净机器；`Use%` 用了 1%。`Filesystem` 列是设备名（这里是示意，virtio 磁盘通常呈现为 `/dev/vdX` 形态，以你机器上的实际名字为准，下一章细讲）。

记住这条输出里藏着的全书铁律：`/data` 是你的**持久盘**，家目录就在 `/data/home`——你所有的练习文件都放这里，原因第 3 章展开。

### 1.6.4 docker info：容器引擎活着吗

```bash
docker info
```

```text
Client:
 Context:    default
 Debug Mode: false

Server:
 Containers: 0
  Running: 0
  Paused: 0
  Stopped: 0
 Images: 0
 Server Version: <版本号以你的机器为准>
 Storage Driver: overlay2
 ...
```

这个命令的判据只有一条：**有没有 `Server:` 段。** `docker info` 会分别报告客户端（你敲的命令）和服务端（后台的 Docker daemon 守护进程）——两段都出现，说明客户端成功连上了 daemon，容器引擎活着，可以愉快地玩耍了。输出很长，但头尾扫一眼那份 `Server:` 就够了，细节（Server Version、Storage Driver、Cgroup 版本等）卷 4 再逐个收拾。

如果只看到 `Client:` 段，然后跟一句 `Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?`，那就是 daemon 没起来——在云电脑上极少见（模板保证它开机自启），真遇到就先 `systemctl status docker` 看一眼服务状态（详见第 13 章《systemd 与服务管理》），十有八九是机器刚创建、服务还没就绪，等半分钟重试。

### 1.6.5 uname -a：这到底是什么机器

```bash
uname -a
```

```text
Linux book 6.18.0-instabox #1 SMP PREEMPT_DYNAMIC Debian 6.18.0-instabox (2025-12-01) x86_64 x86_64 x86_64 GNU/Linux
```

（内核小版本号与编译时间以你的机器为准，这是代表性输出。）

`uname`（unix name）打印系统信息，`-a`（all）是把所有字段都打出来。逐段拆：

| 字段 | 本例的值 | 含义 |
| --- | --- | --- |
| 内核名 | `Linux` | 操作系统内核家族，天经地义是 Linux |
| 主机名 | `book` | 你给机器起的名字 |
| 内核版本号 | `6.18.0-instabox` | **重点看尾巴**：带 `-instabox` 后缀，说明这是平台方定制的内核 |
| 版本信息 | `#1 SMP PREEMPT_DYNAMIC Debian ...` | 编译次数、SMP（对称多处理）支持、编译时间 |
| 架构 | 三个 `x86_64` | 依次是机器架构、处理器特性、硬件平台，三者相同很常见，即 amd64 |

`-instabox` 这个后缀是本章最有意思的细节：它说明这台机器跑的不是"下载下来的标准内核"，而是平台方为 microVM 裁剪调优过的内核。整台机器跑在 **Firecracker microVM**（一种为"海量小虚拟机"设计的轻量虚拟化技术，由亚马逊开源，阿里、腾讯的 Serverless 产品大量使用它）上。翻译成人话：你手上的不是一台"装在虚拟机里的电脑"，而是一台为云计算重新设计过的轻量虚拟机——启动快、隔离好、按秒计费。这也再次印证了 1.1 节说的"与生产环境同构"：你现在操作的方式，就是云时代工程师操作服务器的方式。

五条命令跑完，把输出对照免费档承诺看一遍：4 vCPU 对上 4、7.6GiB 对上 8 GiB 扣除内核预留、20G 对上 20 GiB 持久盘、Docker 活着、内核是定制版。**全部对上，收货。**

> **SRE 贴士**：收到任何一台新机器——新同事的笔记本、新租的 VPS、客户移交的服务器——都该跑一遍这个"五件套体检"：`nproc` 看 CPU、`free -h` 看内存、`df -h` 看磁盘、`docker info` 看容器引擎、`uname -a` 看系统身份。两分钟，建立对这台机器的基线认知。后面排障时你跟"正常状态"一比，异常自己就浮出来了。**"正常长什么样"是你脑子里最重要的参照系。**

把免费档的所有配额摆在一张表里，逐行看懂——这些数字决定了你"能玩多大"，也预先解释了后面所有奇怪的报错：

### 1.7.1 暂停、恢复与 30 分钟锁死的应对

```bash
instabox suspend book    # 暂停：文件、内存、现场全保留，只算存储费
instabox resume book     # 恢复：通常秒级回到离开时的现场
```

`suspend`（暂停）不是关机、更不是删除：你的文件原样保留，内存里的进程状态也保留，`resume`（恢复）之后常常"仿佛什么都没发生过"。计费模型上，暂停期间只算存储费——这是学生党最该摸熟的功能。

而"空闲 30 分钟自动暂停"是平台替学生党省钱的设计：你的 SSH 会话断开、机器没有任何活动，半小时后平台自动把机器挂起。**免费档这个阈值锁死，不能调。** 知道这一点后，正确的姿势不是对抗它，而是利用它：

1. **用完就手动 suspend**——`instabox suspend book` 一个 Tab 补全的事，立刻停在你知道的状态，而不是等它冷不丁自动暂停。
2. **重要节点做快照**（下一节），把进度固化成可回退的环境。
3. **长任务丢到后台跑**（`nohup` + 日志文件，详见第 9 章《进程管理与系统监控》的 tmux 部分），别占着交互终端等。

至于"作业写到一半它自动暂停了怎么办"——慌什么，`instabox resume book` 一条命令的事。暂停不是故障，是常态。**理解计费模型，是云上生存的第一课。**

## 1.8 网页控制台与快照：备份的"板凳位"

### 1.8.1 Computer 标签长什么样

回到网页控制台，核心页面是 **Computer（计算机）**标签：列出你的机器、显示状态（running / suspended 等）、提供创建/暂停/恢复/删除按钮、管理快照。鼠标能做的事情，CLI 都能做，还多两样：一是删除机器时的**二次确认**（防手滑，第 3 章专门说）；二是看机器运行曲线般的状态变化。结论：日常操作以 CLI 为主，控制台留作"确认状态"和"危险操作的第二双眼睛"。

### 1.8.2 快照：把你的进度固化成"板凳位"

```bash
instabox snapshot save book --name base      # 给当前状态的 book 存一份快照，命名 base
instabox create --name job2 --snapshot base  # 从快照开一台新机器
```

第一条命令的含义：把 `book` 当前的环境（系统、软件、`/data` 上的文件）存成一份叫 `base` 的快照。执行时平台会**先把机器停机、保存、再拉起来**（保存前停机，所以那几秒里你的连接会断一下），而且它**只存环境、不存进程现场**——关机前你跑在内存里的东西，快照不负责。

第二条命令：用这份快照开一台新机器 `job2`。这是"复制一份干净环境做对照实验"的标准姿势——比如你怀疑某个配置把机器搞坏了，就从 `base` 开一台新的，两边对比，结论立现。

三条使用纪律：

1. **命名带日期或用途**，比如 `base`、`after-ch03`，半年后你还能认出它是什么进度。
2. **数量克制**：免费档只有 5 个快照名额，全账号（机器+快照）存储上限 200 GB——定期删旧快照，把它当"季度存档"而不是"每日备份"。
3. **快照不是备份**：它是平台侧的整机还原点，方便、但粗。真正的数据备份要"可验证地恢复"，那是第 16 章《防火墙与数据备份》的内容，本书会带你真做一次恢复演练。

> **SRE 贴士**："先存一个基线快照，再动手改"和"改配置前先 `cp` 一份 `.bak`"是同一种思维的两个尺度：前者管整机，后者管单文件。生产环境的黄金法则是——**任何变更之前，先让自己有路可退。**快照、备份、`.bak`、Git commit，都是"退路"的不同价位。

## 1.9 六个坑，逐个拆

这些坑你几乎一定会遇到。提前看过一遍，遇到时你就知道"哦，这集我看过"，而不是"完了，机器坏了，要不要重装系统"。

### 坑一：`403 template_not_allowed`——免费档指定不了模板

**症状**：执行 `instabox create --name x --template universal`（或任何 `--template`），被拒，错误信息里带 `403 template_not_allowed`。

**原因**：模板是付费能力，免费档只给默认模板 `agent-browser`。默认模板该有的都有了（Docker、Node.js 22、Python+uv、Go、Rust、C 工具链、桌面+Chromium），对本书足足够。

**对策**：乖乖用默认模板；真要别的环境，先存快照再从快照开机——**从快照创建机器不受此限**。

### 坑二：`429 quota_exceeded`——并发额度被打满

**症状**：创建或连接机器时被拒，错误码 `429 quota_exceeded`。

**原因**：并发额度是**全账号共享 32**——你名下同时跑着的机器、脚本循环创建的实例，都算在里面。写脚本时不小心循环 `create`、或者开了好几台机器忘了删，都会把额度烧穿。

**对策**：一是列出所有机器，把不用的删掉（或 suspend）；二是写脚本时给循环创建加"存在即跳出"的判断，别让脚本变成"刷额度机"；三是 429 是"稍后重试"信号，等等再来，不是平台坏了。

### 坑三：30 分钟自动暂停——"我作业写到一半呢！"

**症状**：去接杯咖啡回来，终端不动了、网站连不上了，一看控制台：机器已自动暂停。

**原因**：空闲 30 分钟自动暂停，免费档锁死不可调。它是帮你省钱的功能，不是故障。

**对策**：`instabox resume book` 秒级恢复；养成"收工 suspend"的反射；重要进度存快照。另外注意：暂停后连接会断，SSH 会话里的前台任务会随之中断（没写日志的产出就没了）——这就是第 9 章强调"长任务必须丢后台+落日志"的现实理由。

### 坑四：`instabox exec` 单条 10 分钟，退出码 124

**症状**：用 `instabox exec book -- 某个长命令` 跑个耗时任务，10 分钟后戛然而止，退出码 `124`，什么结果都没看到。

**原因**：`exec` 是"不进交互 shell、远程执行单条命令"的模式，单条上限 10 分钟，而且**输出是整批返回、不流式**的——命令没跑完之前，你屏幕上啥也没有（详见第 9 章《进程管理与系统监控》用 nohup 破解这个限制）。

**对策**：短命令（看状态、查文件、验货）放心用 exec；长任务换成 `instabox ssh book` 进交互终端，再用 nohup/tmux 丢后台，配日志文件。判断标准很简单：**这条命令会不会跑超过 10 分钟？会就别用 exec。**

### 坑五：单文件传输 10 MiB——"怎么传个大文件这么难"

**症状**：往云电脑拖一个 20 MB 的安装包/数据集，失败，提示体积超限。

**原因**：单次传输上限 10 MiB，平台按"小文件思维"设计的。

**对策**：三条路——一，本地 `split -b 8M big.tar.gz parts_` 分成几瓣，传过去再 `cat parts_* > big.tar.gz` 拼回来（`split`/`cat` 的用法见第 5 章《文件与目录操作》）；二，大文件根本别用"传输"，用 `git` 管理代码、用 `pip`/`apt` 装软件，让云端自己拉；三，超过 10 MiB 的东西先问自己"我真的需要它吗"——多数时候答案是不需要。

### 坑六：快照不存"现场"——"我跑了一半的服务呢？"

**症状**：`snapshot save` 之前有个服务跑得好好的，从快照开的机器上它没在跑。

**原因**：快照保存前会停机，**只存环境（磁盘上的系统与文件），不存进程现场**。它不是"冻结时间"，是"封存硬盘"。

**对策**：想让服务开机自启，得把它注册成 systemd 服务（详见第 13 章《systemd 与服务管理》）——那才是"跨重启还在"的正经机制；想让脚本继续跑，`resume` 而不是 `snapshot save`。记住这个区分：**resume 保现场，快照保环境。**

> **SRE 贴士**：上面六个坑，四个半最后都收敛到同一句话：**看错误码，别只看"失败了"。** `403 template_not_allowed` 说的是"这个套餐不允许"，`429 quota_exceeded` 说的是"额度满了"，`124` 说的是"超时了"。每个错误码都是一句精炼的人话，只是用机器腔说的。学会读错误码，你的排障效率会翻倍——这条原则从第 1 章一直用到第 17 章。

## 动手练习

以下题目都在你自己的电脑（终端）和 `book` 云电脑上完成。

1. 按 1.3 节装好 CLI，跑 `instabox --version` 与 `instabox --help`，把两者的输出各抄一行进命令笔记本。
2. `instabox login` 完成登录；`instabox create --name book` 创建机器。
3. 依次执行五条验货命令（`nproc`、`free -h`、`df -h /data`、`docker info`、`uname -a`），把输出贴进笔记本，并逐条写一句"我看到 ___，所以 ___"的判读（如：nproc 输出 4，所以平台给了 4 个 vCPU）。
4. 故意触发一次坑：执行 `instabox create --name test1 --template universal`（或当前版本支持的等价格式），把报错原文抄下来，用一句话解释平台为什么拒绝你。完事后若机器真的创建出来了，就把它 suspend 掉。
5. 在 `book` 上执行 `instabox suspend book`（不在 book 里，在你的本地终端执行），再 `instabox resume book`，然后 SSH 进去确认现场还在：`ls /data/home`，`uptime` 看启动时间是否变化。记录你的观察。
6. 综合题：执行 `instabox snapshot save book --name base`，记录平台提示了哪几步（停机/保存/开机）；然后为你的实验环境写下"我的使用三原则"（把本章六个坑各转写成一条对自己有用的规则）。

> **参考答案**：
>
> 1. `--version` 出版本号；`--help` 列子命令清单。抄不抄随意，重点是知道"忘了就查它"。
> 2. 看到 `running`/类似状态即成功；若遇到 waitlist，先完成第 3、4 题的本地部分。
> 3. 判读示例：`free -h` 的 total 约 7.6GiB → 8 GiB 扣除内核预留，正常；`uname -a` 尾巴带 `-instabox` → 定制内核的 Firecracker microVM。每条都要能闭环到配额表。
> 4. 报错形如 `403 template_not_allowed`；解释：免费档只提供默认模板 agent-browser，不允许指定模板；从快照开机不受此限。
> 5. suspend 后 resume 通常秒级；`/data/home` 内容还在；`uptime` 显示的启动时间会是恢复之后的时刻（内存现场虽在，但 uptime 以恢复为准，具体表现以你的机器为准）——重点是确认文件没丢。
> 6. 流程应为"停机 → 保存 → 重新开机"；三原则示例：进度固化用快照、收工必 suspend、长任务丢后台并写日志。
