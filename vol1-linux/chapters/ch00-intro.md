# 第 0 章 导读：什么是 SRE，为什么要从 Linux 开始

> 欢迎打开这本书。这一章我们不碰键盘，先把三件事说清楚：SRE 到底是个什么岗位、你为什么绕不开 Linux、以及接下来六卷书会带你去哪里。磨刀不误砍柴工——很多人学 Linux 半途而废，不是因为命令难，而是一开始就没想明白"我为什么要学、要学成什么样"。想明白的人，命令行就是新大陆；想不明白的人，命令行就是酷刑。

> **本章目标**
> - 能用自己的话解释 SRE（Site Reliability Engineering，网站可靠性工程）的定义与核心思想，并说清 SRE、传统运维、DevOps 三者的关系与分工。
> - 能复述本书六卷路线图：每一卷讲什么、前置是什么，知道自己当前站在什么位置。
> - 能说出本书的学习方法（边敲边记、建立自己的命令笔记本），并了解实验环境与全书的基本约定。

---

## 0.1 这本书写给谁

这本书假设你是一个"没有任何基础的初学者"：可能是在校学生，可能是做测试、开发、网管想转运维，也可能是纯粹对服务器感兴趣。你不需要学过计算机网络，不需要记得住二进制换算，不需要有任何"机房经验"。每一个命令都从"这是什么、长什么样、怎么用"讲起。

同样重要的是先说清楚这本书**不**承诺什么：

- 它不是命令大全。手册是给会查的人用的，本书是给不会的人用的，目标是让你学会查手册并理解看到的内容。
- 它不是某本认证考试的教材。我们按 SRE 真实工作的优先级组织内容，不按考试大纲。
- 它不覆盖所有 Linux 发行版。全书统一使用 Debian 13（代号 trixie）作为实验环境，命令与文件路径以 Debian 系为准。换个版本（比如 RHEL 系）安装命令会有差别，但底层概念九成通用——**概念大于发行版**，这一点后面会反复验证。

如果你能坚持按书里的建议动手把每一章敲完，学完第一卷时，你应该能：熟练登录一台 Linux 服务器，用命令完成日常的查看、查找、编辑、管理操作，写出让系统定时干活的脚本，独立排掉八成"机房新人"级别的故障。这就是本卷的交付物。

## 0.2 SRE 是什么：先回答那个被问烂了的问题

几乎所有运维岗的面试都会问一句："你了解 SRE 吗？"我们把这个问题彻底回答一次。

**SRE（Site Reliability Engineering，网站可靠性工程）最早是 Google 在 2003 年前后创立的岗位与方法论：用软件工程的方法，来保障大规模系统的可靠性。** 起因很朴素：Google 的机器和业务规模太大，靠人盯着屏幕、手工敲命令这种传统运维方式根本撑不住，于是他们决定"招一批软件工程师来做运维"，并且给这批人立下规矩：凡是人需要重复做的事，都必须用代码自动化掉，把人的时间留给工程。

这套做法后来被整理成两本公开的著作——《SRE：Google 运维解密》（Site Reliability Engineering: How Google Runs Production Systems）和《SRE 工作手册》（The Site Reliability Workbook），SRE 这个词才从 Google 内部的一个岗位名，变成了整个行业的一种岗位和方法论。今天你在招聘网站上看到的"SRE 工程师""稳定性工程师""运维开发工程师"，大多是这个岗位的不同叫法。

术语第一次出现，我们都按「中文（English）」的方式标注，之后就可以单独使用了。

理解 SRE，抓住四个关键词就够了：

**第一，可靠性是可以度量的。** "系统很稳"不是态度，是数字。行业用 **SLA（Service Level Agreement，服务等级协议）**描述对外的承诺，用 **SLO（Service Level Objective，服务等级目标）**描述内部的目标值，用 **SLI（Service Level Indicator，服务等级指标）**描述被测量的对象（比如"接口成功的比例"）。比如"SLO：月度可用性不低于 99.9%"，翻译成时间就是：

| 可用性目标 | 一年允许不可用的累计时长 |
| --- | --- |
| 99% | 约 3.65 天 |
| 99.9%（三个九） | 约 8.76 小时 |
| 99.99%（四个九） | 约 52.6 分钟 |
| 99.999%（五个九） | 约 5.26 分钟 |

从"三个九"到"五个九"，代价通常是数量级的上升。每个 SRE 都要在心里装这张表：**可靠性不是越高越好，是"刚好多好"最好。**

**第二，错误预算（Error Budget）。** 追求 100% 可靠是个伪命题——哪怕系统代码全对，光纤也可能被挖断。Google 的思路是：既然达不到 100%，不如把"允许出多少故障"当成一笔预算花掉。SLO 是 99.9%，这个月预算就是 8 小时多一点的"宕机额度"；额度没花完，开发团队可以放心大胆地发新功能；额度提前花光了，全队停止发版，集中精力修质量和补齐监控。错误预算是"速度"与"稳定"之间的平衡器，也是 SRE 跟业务团队讲道理时最有力的一把尺子。

**第三，消灭琐事（Toil）。** 琐事的定义是：手工的、重复的、能自动化的、没有长期价值、而且随着系统规模线性增长的工作。每天手动重启一次服务、每周手动导一次报表、每次上线手动点二十下——这些都是教科书级的琐事。Google 对 SRE 有一条硬规矩：**花在运维性事务上的时间不能超过一半**，剩下的时间必须投入工程改造——做工具、做自动化、消除产生琐事的根源。你未来面试时讲"我把某个重复劳动脚本化了"，比讲"我能熬夜盯机器"加分得多。

**第四，不追责的复盘（Postmortem）。** 出故障不可怕，可怕的是同一个故障出第二次。现代事故复盘（Postmortem）讲究"对事不对人"：事故报告描述的是系统为什么允许这个错误发生，而不是谁该被罚款。只有不怕挨骂，人才敢把真实时间线写进报告；报告里全是真的，系统才真的能被修好。

有了这四个关键词，面试时再被问"什么是 SRE"，就可以这么答：**SRE 是把运维当成软件问题来解的岗位：用可度量的目标定义可靠性，用错误预算平衡速度与稳定，用工程手段消灭重复劳动，用不追责的复盘让系统持续变强。** 这段话你会在第 0 章之后的六卷书里，一遍遍地看到它的落地形态。

> **SRE 贴士**：如果你现在去面 SRE 实习，被问到 SLA/SLO/SLI 的区别，记住这个类比：SLI 是"你体温多少度"（实际测量值），SLO 是"体温不超过 37.3 度"（健康目标），SLA 是"超过 38 度必须就医，否则退挂号费"（对外承诺与违约条款）。三个词一层比一层正式，一层比一层带后果。

> **生产 vs 实验室**：真实公司里，SLO 不是工程师拍脑袋写的，是跟业务方谈出来的，而且常常要先补齐测量能力才能谈。实验室里你自己给自己定 SLO、自己测自己，看起来像过家家——但这套"先定义指标、再想办法逼近指标"的思维，正是从你掌握第一行监控命令那天开始练起的。

## 0.3 SRE、传统运维、DevOps：一张对比表理清关系

初学者最大的困惑是这三个词的关系。先把结论说清楚：**它们不是三个并列的"竞品"，而是同一件事在三个年代的形态。**

- **传统运维**是"手工时代"：人肉值守、纸面流程、出问题登机器、扩容靠加班。它的出发点是"稳"，代价是慢和贵。
- **DevOps（开发运维一体化）是一场文化运动**：主张打破开发与运维之间的部门墙，小步快跑、频繁发布、共同为结果负责。它回答了"应该往哪走"，但没有回答"具体怎么干"。
- **SRE 是这场运动的工程化落地之一**：Google 有句广为流传的表述大意是——"把一个软件工程师放到运维的位置上，让他用工程的方法改造运维，这就是 SRE"。SRE 把 DevOps 的"文化"翻译成了岗位职责、量化指标和一套可复制的工程实践。

一张表把三者摆在一起，重点看最后一行：

| 维度 | 传统运维 | SRE | DevOps |
| --- | --- | --- | --- |
| 关注点 | 系统别宕机，按工单执行 | 用软件方法持续提升可靠性，用数据说话 | 开发与运维协作，又快又稳地交付价值 |
| 常用手段 | 手动操作、零散脚本、值守巡检 | 自动化平台、代码化管理、度量驱动、消除琐事 | CI/CD、持续集成部署、流程与文化改造 |
| 考核指标 | 故障次数、"不出事" | SLI/SLO、错误预算、MTTR、琐事占比 | 发布频率、变更前置时间、变更失败率（即业界常用的 DORA 四指标） |

逐行解释。"关注点"那一行的差别最本质：传统运维的核心动作是"执行与值守"，SRE 的核心动作是"度量与改造"，DevOps 的核心动作是"连接与流动"。"常用手段"那行决定了你的时间花在哪：传统运维的时间花在重复执行上，SRE 的时间花在把重复执行变成系统上，DevOps 的时间花在打通研发到运维的链路上。最该记住的是"考核指标"那一行——**一个团队用什么指标考核你，你就是什么岗位。** 被"故障次数"考核，你干的是传统运维的活；被"变更失败率、平均恢复时间（MTTR，Mean Time To Repair）"考核，你干的是 SRE 的活。国内招聘市场上这三个词经常被混用，区分你真实水平的就是这一行。

还有一个细节值得知道：SRE 并不取代"运维"这项工作本身，而是把它拆开了——重复的、低价值的部分交给自动化和平台，剩下的高价值部分（容量规划、应急决策、架构演进）由工程师承担。**运维没有消失，只是升级了。**

> **SRE 贴士**：评价一个团队"现代与否"，最快的办法是问三个问题：你们的 SLO 是多少？上次故障的复盘报告在哪里看？上线一次要点几下鼠标？三个问题都有干脆答案的团队，大概率已经是 SRE 的工作方式了。

## 0.4 为什么学 Linux 是 SRE 之路的起点

现在回答书名里的问题：为什么这本书从 Linux 讲起，而不是从"容器""监控""报警"这些听起来更时髦的东西讲起。因为四个绕不开的事实：

**事实一：服务器几乎全是 Linux。** 你未来接触的绝大多数服务器——云主机、机房里的物理机、公司内部的测试机——跑的都是 Linux 阵营的系统（Debian、Ubuntu、Red Hat 系等等）。这不是信仰，是市场份额的结果：开源、免费、稳定、生态厚，云厂商默认镜像一半以上是 Linux。

**事实二：云的底座是 Linux。** 你买一台"云电脑""云主机"，本质是在别人的机房里租了一台 Linux 虚拟机，用 SSH（Secure Shell，安全外壳协议）连上去操作。云厂商做了一层漂亮的网页控制台，但控制台背后的每个按钮，最终都翻译成对 Linux 的操作。**学会了 Linux，你就是直接操作云；只会点控制台，你永远隔着一层玻璃。**

**事实三：容器长在 Linux 上。** Docker 和 Kubernetes 之所以能存在，靠的是 Linux 内核提供的能力——命名空间（Namespace）做隔离、控制组（cgroup）限制资源。一个容器本质上就是一个被"圈起来"的 Linux 进程。你不懂 Linux 的进程、文件、网络、日志，容器对你来说就永远是一个"能跑就行"的黑盒；一旦黑盒出了问题，你没有任何排查的手段。

**事实四：你未来要"伺候"的所有软件，全是 Linux 上的进程。** Nginx、MySQL、Redis、Kafka、Prometheus、etcd……这些名字没有一个是操作系统，它们全是"跑在 Linux 上的普通程序"，遵守同一套规矩：有配置文件、有日志文件、有进程、有端口、有权限。学会了怎么伺候一个 Linux 上的程序，你就学会了伺候所有程序。

用一个思想实验收尾：Kubernetes 排障的三板斧——`kubectl describe`、`kubectl logs`、`kubectl exec`，翻译成人话分别是"看系统记录的事件""看进程的输出""进到机器里手动查"。你看，兜兜转转，最后都要落到一个 Linux 环境里看进程和文件。**卷 1 的地基性就在于此：它是后面五卷书的公共语言。** 网络卷要你先会看网卡和端口，数据库卷要你先会看进程和磁盘，容器卷要你先会看文件系统——没有一层是悬空的。

> **SRE 贴士**：常有初学者问"先学 Linux 还是先学 Docker"。答案是绝对的：先 Linux。Docker 镜像里的默认 shell、容器崩掉后你在节点上看到的进程树、卷（Volume）映射到宿主机后的文件权限——这些全考 Linux。跳过 Linux 直接学容器，学到"排障"章节就只能死记硬背别人的排查步骤，说不出为什么。

## 0.5 本书六卷路线图

全书规划为六卷，一条从"会用命令"到"能对生产负责"的完整路径：

| 卷次 | 主题 | 一句话说明 | 前置依赖 |
| --- | --- | --- | --- |
| 第一卷 | Linux | 命令行、文件系统、权限、进程、脚本——SRE 的工作语言，一切的地基 | 无，零基础直接读 |
| 第二卷 | 网络与系统服务 | TCP/IP、DNS、SSH、Nginx、防火墙——让服务可被稳定地访问 | 第一卷 |
| 第三卷 | 数据库与中间件 | MySQL、Redis 等数据系统的安装、备份、排障——数据是业务的最后底线 | 第一卷，建议先过第二卷 |
| 第四卷 | Docker & Kubernetes | 容器化与容器编排——现代交付与扩容的标准形态 | 第一卷、第二卷 |
| 第五卷 | 可观测性 | 指标、日志、链路追踪——让系统"会说话"，让故障可被定位 | 第一卷，有第四卷背景更佳 |
| 第六卷 | SRE 实战 | 值班规范、应急响应、变更管理、容量与成本——从技术走向方法论 | 建议已完成第一、四、五卷 |

怎么用这张表？三条建议：

1. **不要跳卷。** 尤其是第一卷——它不教你任何"能拿去炫耀"的东西，但第二卷之后的每一章都在悄悄用它的概念。
2. **每卷给自己配一个真实交付物。** 比如学完第二卷，你应该能让一台云主机对外提供一个 HTTPS 网站；学完第六卷，你手上应该有一份自己写的值班手册和一次真实故障的复盘报告。**以 deliverable（可交付物）倒逼学习**，比"看完了"扎实得多。
3. **允许并行，不允许跳跃。** 第五卷在你还没碰过容器时也能读个开头，但"容器里怎么采日志"这种问题，最好在有第四卷基础后再回来啃。

你现在的位置：第一卷，第 0 章，一切开始的地方。

> **SRE 贴士**：路线图最大的敌人不是难，是"中间搁置"。六卷书按每天一小时的节奏大约需要一年——这个节奏刚好，因为 SRE 的本事本来就不是冲刺出来的。真正拉开差距的，是那些把"今天敲了三条命令"记进笔记本、并且连续记了三百天的人。

## 0.6 怎么学这本书：四个习惯

同样的教材，有人学完能上岗，有人学完只会划重点。差别几乎全在习惯上。本书从头到尾假设你会坚持下面四条：

**习惯一：边敲边记，建立自己的命令笔记本。** 看十个"精通 Linux"的视频，不如亲手敲错一条命令。准备一个笔记本（纸质或电子都行），每学完一节，把这三样东西记下来：命令、它的最常用参数、一条你自己敲出来的真实输出。日积月累，这就是一本"为你自己定制的手册"——比任何速查表都好用，因为它是从你见过的坑里长出来的。模板长这样：

```markdown
## 查看目录内容 ls
- 最常用：ls -lah /data/home
- -l 长格式 / -a 显示隐藏文件 / -h 人类可读大小
- 真实输出（2026-11-13，book）：
  root@book:~# ls -l /data/home
  total 8
  drwxr-xr-x 2 root root 4096 Nov 13 09:12 notes
```

**习惯二：别只读不动手。** "看懂了"和"会敲"之间隔着一条鸿沟，招聘时不认"看懂"，只认"会敲"。命令行的肌肉记忆（比如"想全文搜索就伸手去打 grep"）只能靠重复形成。本书每个命令块，都请你原样敲一遍，再改几个参数敲第二遍。

**习惯三：允许犯错，并且敢犯错。** 学命令最有效的方式之一，是亲手把错误犯一遍：权限不足到底长什么样、命令拼错会提示什么、文件被删掉还能不能回来——这些"体感"是任何文字描述替代不了的。本书提供的实验环境是一台"弄坏就重建"的云电脑，正是为了让犯错没有代价。记住这个业界流传的比喻（ pets vs cattle，宠物与牲畜）：**把服务器当宠物，每一台都悉心照料、舍不得动；把服务器当牲畜，按需取用、坏了就换。** 现代云计算的可观测性、自动化、无人值守发布，底子都是这个思维。第 1 章我们展开讲。

**习惯四：正视英文，但不害怕英文。** Linux 生态最权威的文档（man page、各项目的官方文档）几乎都是英文，这件事只会英语变好、不会 Linux 变好而改变。本书的原则是：所有概念第一次出现都给「中文（English）」对照，书里的讲解全部用中文；但 man page 和错误信息里的英文，本书会陪你逐段读懂——**读懂错误信息，是 SRE 的核心竞争力之一。** 一台报错的机器对会读错误信息的人是良医，对不会的人是判官。

## 0.7 本书约定

最后是几条阅读约定，先立在这里，避免后面每章重复：

- **实验环境**：全书所有实操统一在一台 InstaBox 云电脑上完成（一台跑在云端的 Debian 13 小主机），注册与开通方法详见第 1 章《搭建实验环境：InstaBox 云电脑》。它免费档配置：4 vCPU、8 GiB 内存、20 GiB 持久盘，写本书的每一章都够用。
- **身份约定**：进入云电脑后默认是 **root**（系统管理员，拥有最高权限）。本书是实验室环境，且云电脑本身就是"坏了就重建"的设计，所以命令默认以 root 身份演示以省去处处写 `sudo`。但请先记住这条原则：**生产环境永远不要直接以 root 操作，要遵循最小权限原则**（先用普通账号，确有必要时临时提权）。到第 5 章《用户、群组与权限》我们会创建普通用户 `bookuser` 并配置 sudo，让你亲手体会多用户模型。
- **提示符约定**：云电脑内的命令提示符统一写作 `root@book:~#`，含义（当前用户是 root、主机名是 book、`#` 表示管理员身份）会在第 2 章《首次登录：SSH、终端与第一组命令》逐段拆解。你本人电脑（Windows/macOS）上的本地终端用 `$` 表示普通用户提示符。提示符本身不写进输出块里。
- **命令块与输出块**：命令块用 ```bash 围栏，输出块用 ```text 围栏；书中的输出是 Debian 13 的代表性真实输出——字段、对齐、换行都按真实系统书写，但具体数值（内存余量、时间戳）会随你的机器略有出入，以你的机器为准。
- **版本号约定**：除内核带 `-instabox` 后缀、Debian 13 / trixie 这些事实外，具体软件版本号（nginx、openssh、systemd 等）一律不写死，以你机器上的实际版本为准。
- **交叉引用**：提到其他章节只写纯文本"详见第 X 章《标题》"，不贴超链接——你可以随时跳过去，也更方便打印。

## 本章小结

本章是全书的"开机自检"，没有命令，但立起了四块基石：**SRE 的定义**（用软件工程的方法做可靠性，关键词是可靠性度量、错误预算、消灭琐事、不追责复盘）；**三者的关系**（传统运维是手工时代，DevOps 是文化运动，SRE 是工程化落地，用考核指标一行就能区分你是哪种活法）；**Linux 的必然性**（服务器、云、容器、数据库全家长在 Linux 上，第一卷是后面五卷的公共语言）；**学习方法**（边敲边记建命令笔记本、动手优先、允许犯错、正视英文）。下一章，我们花二十分钟，把写完全书要用的实验环境搭起来。
